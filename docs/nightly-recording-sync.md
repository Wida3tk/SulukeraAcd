# Daily recording synchronization

Enabled October 18, 2026 at the user's explicit request. Discovery is scheduled with `0 20 * * *` (UTC), which is 23:00 in Saudi Arabia. It checks the three configured Zoom hosts once per Saudi calendar day. Attendance and the existing grade/exam schedules are unchanged. The first scheduled discovery remains due at 23:00; operator preview does not consume/claim that day's scheduled run.

`nightly_recording_runs` stores the daily claim/result. `nightly_recording_jobs` stores only safe manifests and status, without OAuth tokens, download URLs or resumable session URLs. `nightly_recording_lock` coordinates continuation. A separate `*/2 * * * *` trigger does at most two existing 8 MiB upload steps for one queued file; when idle it makes no Zoom/Drive requests. Continuation is not account discovery. Upload steps refresh exact meeting-recording metadata by UUID rather than repeatedly searching the host's whole recording list. A first-time transfer still validates that the source is in the requested host's catalog. Daily discovery covers the last fourteen days, including across month boundaries, to catch recordings that become ready late; unfinished existing transfers can still resume by UUID after leaving this discovery window.

Explicit meeting/account/course/folder mappings cover the six academic courses and professional foundations. Only published lessons with matching date and configured meeting ID are queued. Shared Q2/Q3 lectures share a single uploaded file. Existing reviewed rescheduling anchors prevent a future course_08 recording from being attached to the wrong lecture number while its schedule remains inconsistent. Multiple lessons for one subject on the same date, ambiguous professional sessions and split videos are held for review, not guessed. The graduation-project meeting remains excluded. Already completed transfers and existing recording links are retained without uploading duplicates.

Academic publication uses the existing guarded update of recording URL only. Professional publication uses a validated virtual target (`pro:track_n:unit_n:session_n`) and conditionally writes only that session's `recordingUrl` leaf, preserving all progress, attendance, grades and other session fields. Professional date, meeting ID, published state and absence of a competing manual link are rechecked before final publication. The existing private playback service verifies size, parent folder, MP4 signature and byte-range access before publication. Zoom source files and Drive sharing are not deleted or modified.

Failures are bounded to five transfer attempts and surfaced as review items. A later nightly pass can reconsider a review after configuration/authentication is corrected. Daily discovery errors are visible in the run summary instead of being reported as successful. No paid plan or billing settings are changed. Google authorization must remain valid; revoked/expired authorization appears as an account error and requires reconnection.

Administration → Lectures and assignments → “حالة مزامنة التسجيلات” exposes enabled state, Saudi time, recent daily runs and queued/retained/review items. It requires an authenticated administrator. It never returns stored secrets or upload session URLs.

Readiness preview found all three accounts accessible: eight previous transfers complete, three professional recordings retained, one graduation recording excluded, no new upload needed. Preview is read-only for content/links and leaves the scheduled run unclaimed. Unit tests cover timezone, once-daily discovery, idle behavior, bounded continuation, course/account isolation, existing-link protection, professional leaf-only ETag writes and known schedule ambiguity. Existing coursework, recording and attendance tests remain required.
